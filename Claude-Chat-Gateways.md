# Claude Chat Gateways — Decisions & Options Log

Raw running log for the multi-platform chat gateway project (Discord done, Teams built 2026-07-15 paused on Azure subscription, Telegram Work live since 2026-07-15). Kept up to date as decisions get made so we don't re-litigate them next time. See [[2026-07-15]] daily note.

## Goal

Let `/loop` and other SDLC/Claude Code work be dispatched and monitored from a phone or chat client instead of needing a terminal open. Same underlying idea as the existing Discord `claude-gateway` — extend it to Teams and Telegram.

## Architecture (shared across all three platforms)

- **Persona model**: each chat/channel/conversation maps to a persona — `workdir` + a fixed Claude session UUID + optional `system_prefix` + `context_files`. Defined in `gateway_personas.json` per gateway.
- **Execution model**: every inbound message spawns a fresh subprocess `claude --resume <uuid> --print`, prompt piped via stdin, stdout captured and sent back as the reply. Not a persistent live session — continuity comes from Claude's own `--resume` plus an in-memory rolling conversation history the gateway maintains and re-injects into every prompt.
- **Command set** (same across platforms): `!status`, `!resume`/`!sessions`/`!list`, `!reset`/`!new`/`!clear`, `!new-session`, `!rename`, `!safe`/`!unsafe`/`!permissions`, `!cron add/list/pause/resume/delete/run`, `!schedule`, `!kill`, `!reload`, `!personas`, `!skill`/`!skill clear`, `!help`.
- **Permission default**: autonomous (`--dangerously-skip-permissions`) on all three platforms — no way to answer an approval prompt over chat. **This required an explicit, separate user confirmation for each platform** (Teams asked 2026-07-15, Telegram asked 2026-07-15) — porting the default silently from an already-approved platform is not sufficient authorization; Claude Code's safety classifier blocks it until asked directly per platform.

## 🐛 Real bug found + fixed same day: stdout/stderr pipe deadlock in ALL THREE gateways

User reported: a "what are my tickets doing" query in Telegram took 500+ seconds, while the same question in the Claude CLI directly takes ~1s via the `my-tickets-status` skill (`c:\projects\skills\my-tickets-status`). Diagnosed by reading the actual session transcript directly (`C:\Users\MarthinusR\.claude\projects\c--Projects-SDLC\10355a1d-786f-4e80-a7b0-19457df024fd.jsonl`) rather than guessing:

1. **Found the skill actually worked, with a real sub-bug**: first attempt ran `python c:\projects\skills\my-tickets-status\scripts\status.py` (Windows backslashes) → exit code 2, path got mangled to `C:\Projects\SDLC\projectsskillsmy-tickets-statusscriptsstatus.p...` — this is the exact "LLM Path Hallucination" pitfall already documented for Hermes (`p-hermes-gateway-pitfalls/SKILL.md`: *"LLMs struggle with Windows `\` in prompts... fusing adjacent path segments"*), just newly hit by this skill's own instructions. Second attempt self-corrected to forward slashes and succeeded.
2. **Found the real, bigger bug**: Claude's own answer was fully written by 06:57:42 — about 90s after the user's message — but the user didn't receive it until ~500s. The delay was entirely inside the gateway, after Claude finished.
3. **Root cause**: `gateway.py`'s `run_claude()` (identical code in all three gateways — Discord, Teams, Telegram) spawns the CLI with `stdout=PIPE, stderr=PIPE`, but only drains stdout (`for raw in iter(proc.stdout.readline, b""): ...` to EOF) and reads stderr **afterward**. If the child process writes enough to stderr to fill the OS pipe buffer (~64KB on Windows) before stdout closes, the child blocks writing to the full stderr pipe while the gateway thread is blocked reading stdout — a classic two-pipe deadlock that only resolves when something external breaks the standoff. This exactly explains highly variable multi-hundred-second delays on an answer that was actually ready in ~90s.
4. **This bug was in the original Discord gateway code from before this project even started** — carried forward unchanged into Teams and Telegram when the architecture was ported. Discord had likely just never hit a query with enough stderr output to trigger it.

**Fix applied to all three** (`claude-gateway`, `teams-gateway`, `telegram-gateway-work`): drain stdout and stderr concurrently on separate daemon threads instead of sequentially, so neither pipe can back-pressure the other. Verified `py_compile` clean on all three. `telegram-gateway-work` (the only one currently live) restarted with the fix — confirmed process alive, persona loaded correctly. `claude-gateway` (Discord) was not running at the time, so the fix takes effect on its next natural start; `teams-gateway` isn't live yet (paused on Azure subscription).

Also fixed the underlying skill bug: `c:\projects\skills\my-tickets-status\SKILL.md` line 26 used a raw Windows backslash path in its documented command — changed to forward slashes (`c:/projects/skills/my-tickets-status/scripts/status.py`) plus an explicit anti-hallucination guard comment, matching the pattern already established in the Hermes pitfalls skill.

**Committed and pushed**: commit `6659d0b` "fix: read subprocess stdout+stderr concurrently to avoid pipe deadlock" — 3 files changed (one per gateway), 64 insertions/14 deletions, pushed to `origin/main`.

## ✨ `!btw` side-channel query, built 2026-07-15/16

User wanted a `/btw`-style side question while a main gateway query is still running — confirmed via question that this should be a one-shot side query (not a true mid-task interrupt, which Claude Code's `--print` mode can't support anyway). Design: reads the busy session's transcript JSONL directly (read-only, no `--resume` collision risk), then answers via a **separate, fresh, tool-free** `claude --print --tools ""` call (first version allowed tool calls and took ~2 minutes doing its own live lookups — defeating the point; restricting to transcript-only + `--tools ""` made it fast, verified via a standalone smoke test). Required `concurrent_updates=True` on the Telegram `Application` (off by default) plus a per-chat `asyncio.Lock` so `!btw` can jump the queue while normal messages stay serialized against each other. **First background-agent build attempt was correctly blocked** by the safety classifier for asserting an unverifiable prior permission confirmation in its own code — same pattern as the Teams/Telegram builds earlier; re-confirmed directly in the main session and built there instead.

**⚠️ Discovered 2026-07-16: this entire feature had silently vanished — never actually committed, and gone from the working file too.** While building the natural-language `!cron` fallback (below), a routine grep for `run_btw_query` came back empty. Checked every commit via `git show <sha>:telegram-gateway-work/gateway.py | grep -c btw` — 0 everywhere. The whole mechanism (`!btw`, `get_chat_lock`, `concurrent_updates(True)`, the `_handle_normal_prompt` split) had been lost, most likely to a stale-file restart somewhere along the way. Surfaced to the user directly rather than quietly rebuilt without mention. Rebuilt from the validated design above, this time actually committed (`530035b`, AIOS repo). **Lesson**: for a live, hand-verified feature that isn't yet committed, treat "commit it" as part of finishing the feature, not an optional follow-up — an uncommitted change on a frequently-restarted process is one bad restart away from disappearing.

Implemented on `telegram-gateway-work` only — **not yet ported to Teams/Discord gateways.**
