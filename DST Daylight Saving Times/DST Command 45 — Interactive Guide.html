DST — Command 45 Architecture & Code Paths

UpdateAssetTimezoneDeviation · 4 entry points · Config.Api delivers to device

What is Command 45?

Command 45 = UpdateAssetTimezoneDeviation — tells a device its timezone offset relative to the org timezone, both before and after a DST transition.

Param1
Seconds offset before DST change
SiteOffset − OrgOffset (pre-transition)
Param2
Seconds offset after DST change
SiteOffset − OrgOffset (post-transition)
Param3
Unix timestamp of DST transition
946688400 = "no DST" in Windows
Key fact

Config.Api calculates all three params itself from the asset's site timezone. You never need to compute them manually.

Entry 1 — UI / API Events

Nine call sites in DynaMiX.Backend. All funnel into DeviceIntegrationManager.UpdateAssetTimezoneDeviation().

Triggered by moving assets, editing sites, merging sites, commissioning, config group changes, and mobile app updates.

Entry 3 — Nightly Service

DaylightSavingAdjustmentService — runs at 00:00:01 daily in DynaMiX.Backend.

Skips assets that already received a correct command this year. Routes through DeviceIntegrationManager same as Entry 1.

Entry 2 — Windows Tool

DaylightSavingsTimeAdjusterNew — redesigned 2023 (CONFIG-3387). WinForms, runs on jumpbox.

Calls Config.Api directly via MiX.ConfigInternal.Api.Client. Two-step: get outdated → send.

Entry 4 — Command Line ⚠️

DaylightSavingsTimeAdjusterCommandline — loops every N minutes until EndDate.

⚠️ SILENTLY STOPS when EndDate expires — no error, no alert

Fix: RDP to HSSYDATS02 → open C:\Projects\DST Command Line\appsettings.json → update EndDate.

Entries 2 & 4 — Direct to Config.Api

// Windows Tool (Entry 2) or Command Line (Entry 4)
// No Backend involved — calls Config.Api via MiX.ConfigInternal.Api.Client

// Step 1: find outdated assets (Config.Api calculates correct params)
MobileUnitCommandsRepository.GetAssetsWithOutdatedDaylightSavingsCommands(
    authToken,
    new DaylightSavingsCommand { GroupIds = "", MobileUnitIds = "123,456", TypeIds = "" }
)
// Returns: List<AssetWithoutDST> — each item has Param1/Param2/Param3 pre-calculated

// Step 2: send (params came from step 1 — no manual calculation)
MobileUnitCommandsRepository.SendCommandsToAssetsWithOutdatedDaylightSavingsCommands(
    authToken,
    assets.Select(a => new AssetDSTCommand {
        GroupId = a.GroupId, MobileUnitId = a.MobileUnitId,
        IsRemoteCommandConnected = a.IsRemoteCommandConnected,
        Param1 = a.Param1, Param2 = a.Param2, Param3 = a.Param3   // straight from step 1
    }).ToList()
)
// Returns: List<string> errors — empty = all sent OK

Silent skip rules — assets that receive no command and no error

✗ Asset missing BASE_FM_FUNCTIONALITY and BASE_MESA_FUNCTIONALITY logical device → silently skipped
✗ Asset missing REMOTE_COMMAND logical device → logged at Debug level as FAILURE, not sent
✗ Already received correct DST command this year (Entry 3 only) → skipped to avoid duplicates
Bottom line for Cornell

Config.Api handles all param calculation. You pass asset/group IDs and it figures out the timezone offsets. You never touch Param1/Param2/Param3 directly.

DTOs

class DaylightSavingsCommand {
    string GroupIds;      // comma-separated group IDs, or ""
    string MobileUnitIds; // comma-separated asset IDs, or ""
    string TypeIds;       // e.g. "MiX4k", or ""
}

class AssetWithoutDST {     // returned by step 1
    long GroupId, AssetId, MobileUnitId;
    string OrganisationName, AssetDesciption, MobileDeviceTypeDescription;
    bool IsRemoteCommandConnected, MesaHasUniqueIdentifier;
    uint Param1, Param2, Param3;  // correct values — use as-is in step 2
    string Status;                 // "Command Incorrect", "Empty Command", etc.
}

class AssetDSTCommand {      // sent in step 2
    long GroupId, MobileUnitId;
    bool IsRemoteCommandConnected;
    uint Param1, Param2, Param3;  // copy from AssetWithoutDST
}

Did Command 45 actually reach the device?

MiX4000 = Mesa path. Commands are queued in [DeviceConfiguration.DataProcessing].[state].[MobileUnitMessage] and tracked through [state].[MobileUnitMessageStateHistory]. Run this query after calling the client method to confirm the command was dispatched.

SQL — Quick check for a specific MiX4000

-- Quick check — did Command 45 get queued for this asset?
SELECT TOP 20
    mum.CreationDateUtc,
    mum.MobileUnitId,
    mum.ParamsJson,
    mumh.MessageStatus,
    mumh.MessageStatusDateUtc
FROM [DeviceConfiguration.DataProcessing].[state].[MobileUnitMessage] mum
LEFT JOIN [DeviceConfiguration.DataProcessing].[state].[MobileUnitMessageStateHistory] mumh
    ON mumh.MessageId = mum.MessageId
WHERE mum.ParamsJson LIKE '%"CommandId":45,%'
  AND mum.MobileUnitId = 5458996954334640037   -- ← replace with your unit ID
ORDER BY mum.CreationDateUtc DESC, mumh.MessageStatusDateUtc DESC
Where to run this

Connect to DSINTSQL01 (INT) or the DataProcessing DB for your environment. Windows integrated auth — no password needed from the dev machine.

Reading the results

MessageStatus Meaning What to do
22 — Created Queued in DB, not yet sent to device Wait — normal if just sent
4 — Sent Dispatched to device, awaiting response Wait — device may be offline
9 — Received Device received the command Good — processing
13 — Acknowledged Device confirmed and applied the offset Done — DST set correctly
25 — Complete Fully processed Done
14 — Expired Command timed out, device never responded Device offline? Resend.
No rows at all?

The command never reached the database. The failure happened before dispatch — check: auth token valid? Asset has REMOTE_COMMAND logical device? Asset has BASE_MESA_FUNCTIONALITY?
